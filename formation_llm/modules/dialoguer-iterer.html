Parcours 2 · Dialoguer efficacement · Étape 3 · NOVICE-FIRST

Un prompt s’améliore par des tests, pas au feeling

Modifier un prompt jusqu’à obtenir une belle réponse ne suffit pas. Une itération robuste ressemble à une petite expérience : observer un échec, formuler une hypothèse, tester une modification ciblée sur plusieurs cas, puis conserver ou annuler selon les résultats.

P2S3 novice-ready≈ 50–65 minAucun appel réseau
Mission

À la fin, vous devrez pouvoir comparer deux versions d’un prompt sur un même jeu de tests, expliquer ce qui a réellement changé et repérer une amélioration locale qui cache une régression ou un sur-ajustement.

Vous devez déjà savoir
Spécifier et exemplifier

P2S1 a posé le contrat de tâche ; P2S2 a introduit few-shot, contrastes, frontières et format de sortie.

Vous allez apprendre
Construire une boucle d’évaluation

Baseline, échec observé, hypothèse, test représentatif, modification minimale, régression et décision.

Critère de réussite
Justifier une modification par des preuves

Vous saurez dire pourquoi une version est meilleure sur un jeu de cas constant, sans l’optimiser uniquement pour l’exemple qui a échoué.

01

Le piège : « ça semble mieux » n’est pas une mesure

Une sortie réussie peut masquer des échecs ailleurs, surtout si vous avez modifié le prompt pour ce seul cas.

Intuition Vous testez un classifieur sur « Mon export CSV est vide ». Il répond QUESTION au lieu de BUG. Vous ajoutez une phrase, retestez ce même ticket et obtenez BUG. Avez-vous amélioré le prompt ? Vous ne le savez pas encore.

Pour conclure, il faut rejouer aussi les cas qui fonctionnaient déjà. La nouvelle règle peut avoir corrigé l’échec ciblé tout en créant une régression sur un autre type d’entrée.

Une itération utile transforme donc une impression en comparaison : même tâche, mêmes cas, même critère, une modification identifiable.

①
ObserverQuel comportement précis échoue ?
②
ExpliquerQuelle cause plausible formulez-vous ?
③
ModifierQuel changement minimal teste cette hypothèse ?
④
ComparerLe gain tient-il sur tout le jeu de tests ?
Question formateur. Demander : « Si le ticket fautif passe après la modification, quelle information manque encore pour dire que le prompt est meilleur ? » Faire émerger spontanément la nécessité de rejouer les cas déjà réussis.
02

Six repères pour transformer le prompting en petite démarche expérimentale

Le vocabulaire sert à raisonner sur les modifications, pas à industrialiser prématurément l’activité.

Baseline

Version de départ du prompt et résultats obtenus avant modification.

Rôle : sans baseline, « mieux » n’a aucun point de comparaison.

Échec observé

Cas concret où la sortie ne respecte pas un critère de réussite défini.

Exigence : décrire le symptôme avant d’imaginer la correction.

Hypothèse

Explication testable de l’échec : frontière mal définie, contexte manquant, format ambigu, exemple trompeur…

Question : « Si cette cause est vraie, quel petit changement devrait aider ? »

Jeu de tests

Petit ensemble d’entrées représentatives : cas normaux, contrastifs, frontières, hors domaine et échecs déjà rencontrés.

Principe : le jeu doit ressembler aux situations réellement importantes, pas seulement aux cas faciles.

Modification contrôlée

Un changement ciblé entre deux versions : une règle, un exemple, une contrainte ou une structure.

Pourquoi ? Si plusieurs variables changent ensemble, on ne sait plus ce qui explique le résultat.

Régression

Un comportement auparavant correct devient moins bon après la modification.

Réflexe : toujours rejouer les anciens cas réussis, pas seulement le cas qui motivait la correction.

03

Exemple travaillé : corriger un échec sans casser le reste

Nous comparons deux versions sur le même mini-banc de tests.

Tâche. Classer un ticket en BUG, FONCTIONNALITÉ, QUESTION ou À_CLARIFIER.

1

Mesurer la baseline

Six tickets sont testés. Quatre sont bien classés ; deux messages ambigus sont forcés dans une catégorie.

Baseline : 4 / 6. Les deux échecs partagent le même symptôme : information insuffisante.
2

Formuler une hypothèse

« La règle décrit les catégories normales mais n’indique pas clairement quand utiliser À_CLARIFIER. »

Important : c’est une cause possible, pas encore une conclusion.
3

Modifier une seule variable

Ajouter : « Si les informations ne permettent pas de distinguer au moins deux catégories plausibles, réponds À_CLARIFIER. »

Contrôle : modèle, paramètres, exemples et autres instructions restent identiques.
4

Rejouer les six cas

Les deux tickets ambigus passent désormais, et les quatre anciens cas réussis restent corrects.

Résultat : 6 / 6 sur ce mini-jeu ; aucune régression détectée ici.
5

Rester prudent

Six cas ne prouvent pas une robustesse universelle. La modification est conservée parce qu’elle améliore un critère sur le jeu disponible, pas parce qu’elle serait « parfaite ».

Suite : tout nouvel échec réel peut devenir un nouveau cas de test, à condition de conserver aussi les anciens.
Décision : conserver la règle de clarification, versionner le prompt et garder les six cas comme garde-fou de non-régression.
04

Iteration Lab — quelle modification mérite d’être conservée ?

Simulation pédagogique : choisissez une seule modification, puis comparez-la à la baseline sur les six mêmes cas.

Baseline : 4 / 6

T1 BUG simple ✓ · T2 FONCTIONNALITÉ ✓ · T3 QUESTION ✓ · T4 frontière ✕ · T5 hors domaine ✕ · T6 BUG contrastif ✓

Résultats simulés

Lecture. Un score n’est utile que si vous pouvez expliquer ce qui a changé et vérifier les régressions.
Débrief formateur. Faire comparer A et D : les deux peuvent afficher un bon score, mais D ne permet pas d’attribuer l’amélioration à une cause précise. Puis demander pourquoi B reste fragile malgré l’amélioration de T4 : il sur-apprend potentiellement un exemple sans traiter le hors domaine.
05

Je complète — quelle est la prochaine action expérimentale ?

Choisissez le geste qui produit l’information la plus utile pour décider.

Un cas échoue mais vous ne savez pas pourquoi.→
Vous avez changé rôle, exemples et format en même temps ; le score augmente.→
Le cas fautif passe après correction.→
Le prompt réussit dix cas faciles mais échoue sur les situations réellement fréquentes.→
06

Six pièges qui transforment l’itération en sur-ajustement

Le but n’est pas de faire monter un score à tout prix, mais d’obtenir une amélioration explicable qui généralise mieux.

« Le cas qui échouait passe : problème résolu »

Vous avez seulement vérifié l’exemple qui a motivé la modification.

Correction : rejouer l’ensemble du banc pour détecter les régressions.
« Je change trois choses, puis je garde si le score monte »

Le résultat ne permet plus de savoir quelle modification a aidé ou nui.

Correction : isoler autant que possible une variable entre deux versions.
« Mon jeu de tests est bon puisqu’il est grand »

Un grand ensemble de cas faciles peut être moins utile qu’un petit ensemble représentatif.

Correction : couvrir cas normaux, frontières, hors domaine et échecs réels.
« Le score global suffit pour comprendre l’amélioration »

Deux versions à 90 % peuvent échouer sur des cas très différents.

Correction : lire les erreurs par catégorie et conserver la trace des régressions.
« J’ajoute chaque cas de test au prompt comme exemple »

Vous risquez d’adapter le prompt aux tests visibles au lieu d’améliorer la règle générale.

Correction : distinguer exemples de guidage et cas réservés à l’évaluation.
« Un seul passage par test mesure parfaitement un comportement »

La génération peut varier ; selon l’enjeu, plusieurs exécutions ou une configuration plus déterministe peuvent être nécessaires.

Correction : adapter le protocole à la variabilité et garder les paramètres constants pendant la comparaison.
07

Expliquez avec vos mots

Votre explication doit montrer que vous savez distinguer correction locale et amélioration générale.

08

Récupération active — raisonner comme un expérimentateur

Le feedback porte sur la qualité de la preuve, pas seulement sur le vocabulaire.

1. Après une première sortie insatisfaisante, le meilleur point de départ est…
Pourquoi ? L’échec observé fournit le signal à expliquer. Modifier avant de le caractériser empêche de savoir ce qu’on essaie réellement de corriger.
2. Pourquoi changer une seule variable à la fois est-il utile ?
Pourquoi ? Une comparaison contrôlée relie plus clairement cause supposée et effet mesuré.
3. Un jeu de tests utile doit surtout…
Pourquoi ? La taille seule n’assure pas la couverture des comportements qui comptent réellement.
4. Le ticket fautif passe avec la nouvelle version. Avant de conserver la modification, il faut…
Pourquoi ? Une amélioration locale peut provoquer une régression ailleurs.
5. Ajouter directement tous les cas d’évaluation comme exemples dans le prompt risque surtout de…
Pourquoi ? Les cas d’évaluation doivent garder une fonction de contrôle ; les transformer tous en démonstrations brouille la mesure de généralisation.
6. Deux versions obtiennent 5/6 mais n’échouent pas sur le même cas. La bonne conclusion est…
Pourquoi ? Un score identique peut masquer des profils d’erreurs différents et des régressions importantes.
09

Transfert — quatre décisions d’itération

Choisissez l’action qui produit la preuve la plus utile sans contaminer l’évaluation.

Résumé pédagogique

Une nouvelle contrainte corrige la longueur excessive mais certains résumés perdent maintenant une idée indispensable.

La longueur s’améliore mais un autre critère se dégrade : il faut arbitrer la régression, pas célébrer seulement le gain.

Assistant administratif

Vous avez ajouté un rôle, trois exemples et une nouvelle règle ; le score passe de 70 à 85 %.

Le gain est réel sur le score, mais sa cause est inconnue tant que les changements ne sont pas isolés.

Classification d’emails

Le banc contient surtout des messages très courts alors que les emails réels sont souvent longs, ambigus et contiennent plusieurs demandes.

Une évaluation non représentative peut donner un excellent score sans mesurer le comportement réellement attendu.

Extraction structurée

Chaque échec du banc est immédiatement copié comme nouvel exemple few-shot dans le prompt.

Tous les tests ne doivent pas devenir des démonstrations : conservez des cas servant uniquement à vérifier la généralisation et les régressions.
10

À retenir : une modification de prompt est une hypothèse à éprouver

La boucle doit rendre les gains visibles, les régressions détectables et les décisions réversibles.

1. Commencez par une baseline.

Sans point de départ mesuré, vous ne pouvez pas démontrer une amélioration.

2. Décrivez l’échec avant de corriger.

Le symptôme et le critère violé doivent être explicites.

3. Formulez une hypothèse testable.

La modification doit avoir une raison, pas seulement être plausible ou élégante.

4. Modifiez le minimum nécessaire.

Une variable identifiable rend la comparaison plus interprétable.

5. Rejouez un jeu représentatif.

Cas normaux, frontières, hors domaine et erreurs historiques servent de mémoire de non-régression.

6. Conservez ou annulez selon les preuves.

Une itération est réversible ; une hausse locale ne justifie pas automatiquement une nouvelle version.
